# Architecture Pipeline

> نقشه‌ی کامل سیستم از منبع داده تا ارسال پیام، و مسیر ۴ فازی توسعه. جزئیات کامل در `docs/architecture.md`.

## لایه‌های pipeline (طراحی هدف، نه همه پیاده‌سازی‌شده)
1. **منابع داده** — CRM/فروشگاه‌ساز، اینستاگرام DM، واتساپ، پیامک، سبد خرید، تاریخچه‌ی سفارش.
2. **لایه‌ی سیگنال‌سازی** — استخراج intent از مکالمه، RFM، چرخه‌ی خرید، تشخیص سبد رهاشده. *(نسخه‌ی ساده‌ی فعلی: تگ intent در داده‌ی نمونه — [[entities/data-model]])*
3. **موتور تصمیم Next-Best-Action** — فاز MVP: rule-based ([[entities/next-best-action-engine]]، [[concepts/decision-rules]]). فاز بعد: امتیازدهی یادگیری‌شونده (uplift modeling/contextual bandit) بدون از دست دادن توضیح‌پذیری.
4. **تولید پیام** — فعلاً قالب ثابت فارسی per-offer/per-channel در `MESSAGE_TEMPLATES`. فاز بعد: LLM برای تنوع بیشتر.
5. **ارسال (Channel Dispatch)** — خارج از scope فعلی؛ نیاز به قرارداد API رسمی متا/واتساپ.
6. **حلقه‌ی یادگیری** — خارج از scope فعلی؛ یادگیری وزن‌ها از نتیجه‌ی واقعی ارسال‌ها.

## فازهای توسعه
| فاز | محتوا | وضعیت |
|---|---|---|
| ۱ (این رپو) | موتور rule-based + داده‌ی نمونه + API محلی | ✅ پیاده‌سازی‌شده |
| ۲ | اتصال واقعی به فروشگاه‌ساز ایرانی + اینستاگرام/واتساپ Business API برای پایلوت | ⏳ |
| ۳ | یادگیری وزن‌ها از نتیجه‌ی واقعی (A/B) | ⏳ |
| ۴ | لایه‌ی افقی چندکاناله + مدل داده‌ی مشترک بین فروشگاه‌ها | ⏳ |

## نکات امنیت/حریم خصوصی (طراحی هدف)
- داده‌ی مکالمه/مشتری نیاز به رمزنگاری at-rest/in-transit و کنترل دسترسی per-tenant دارد.
- opt-in هر کانال مستقل رعایت شود (سیاست متا برای واتساپ Business API).
- `do_not_disturb` باید override قطعی روی همه‌ی تصمیم‌ها باشد — **پیاده‌شده** در موتور فعلی ([[entities/next-best-action-engine]]).
