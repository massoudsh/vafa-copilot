# وفا (Vafa) — کوپایلوت هوشمند رشد و حفظ مشتری برای خرده‌فروشی

به‌جای تخفیف کور برای همه، برای هر مشتری بهترین اقدام بعدی را پیدا می‌کنیم: چه کسی، چه زمانی، از چه کانالی، با چه پیشنهادی.

## محتوای این رپو

| بخش | توضیح | مسیر |
|---|---|---|
| پیچ‌دک | ارائه‌ی ۱۰ اسلایدی فارسی برای سرمایه‌گذار/تیم | [`outputs/vafa-pitch-deck.pdf`](outputs/vafa-pitch-deck.pdf) |
| معماری فنی | نقشه‌ی کامل سیستم از منبع داده تا ارسال پیام | [`docs/architecture.md`](docs/architecture.md) |
| MVP — موتور تصمیم | موتور rule-based و قابل‌توضیح next-best-action + داده‌ی نمونه + API | [`mvp/`](mvp/) |
| لندینگ‌پیج | صفحه‌ی معرفی محصول برای اعتبارسنجی بازار | [`landing/index.html`](landing/index.html) |

## اجرای سریع MVP

```bash
# از ریشه‌ی مخزن؛ اجرای دمو با تاریخ ثابت داده‌های نمونه
python3 mvp/engine/next_best_action.py --as-of 2026-07-24

# نصب وابستگی‌های API و تست
python3 -m venv .venv
.venv/bin/pip install -r mvp/requirements-dev.txt
.venv/bin/python -m unittest discover -s mvp -p 'test_*.py' -v

# اجرای API در محیط توسعه‌ی خودتان
.venv/bin/uvicorn mvp.api.main:app --port 8000
```

## API و داده‌ی آزمایشی

این پروژه یک دموی **فقط‌خواندنی** است، نه سرویس آماده‌ی تولید؛ همه‌ی ۱۷ مشتری و مکالمه‌ها ساختگی‌اند و هیچ پیامی ارسال نمی‌شود. تاریخ مرجع داده‌ها `2026-07-24` است. بدون `as_of` موتور از تاریخ روز استفاده می‌کند؛ برای بازتولید دمو از تاریخ مرجع استفاده کنید. تغییر تاریخ فقط زمان ارزیابی سیگنال‌ها را عوض می‌کند، نه snapshot فیلدهای تجمیعی مشتری؛ این قابلیت بک‌تست تاریخی نیست.

| مسیر GET | نتیجه |
|---|---|
| `/` | وضعیت سرویس |
| `/demo` | تاریخ snapshot، تعداد مشتریان و توزیع ۹ نوع اقدام |
| `/analytics?as_of=2026-07-24` | خلاصه‌ی داشبورد: تعداد کل، قابل اقدام، فوریت، کانال، شهر و نوع اقدام |
| `/analytics?urgency=high&city=تهران` | همان خلاصه با فیلتر فوریت و شهر |
| `/next-best-action?as_of=2026-07-24&action_type=care&channel=whatsapp` | فهرست پیشنهادها با فیلتر نوع اقدام، فوریت، کانال یا شهر |
| `/dashboard` | همان لندینگ/داشبورد؛ وقتی API این فایل را سرو کند، داده از `/next-best-action` خوانده می‌شود |
| `/openapi.json` | قرارداد پاسخ‌ها و پارامترها |
| `/docs` و `/redoc` | مستندات تولیدشده‌ی API |

تاریخ نامعتبر پاسخ ۴۲۲ دارد. نمونه‌ی خروجی آماده: [`mvp/demo-actions.json`](mvp/demo-actions.json). تست‌ها با HTTP درون‌پردازه‌ای اجرا می‌شوند؛ نیازی به مرورگر یا سرور دائمی ندارند.

قواعد ایمنی: عدم مزاحمت و نبود رضایت، همه‌ی پیام‌ها را متوقف می‌کند. چهار پیام در ۳۰ روز همه‌ی پیشنهادهای فروش را متوقف می‌کند، اما رسیدگی به شکایت با رضایت همچنان اولویت دارد. رویداد آینده نادیده گرفته می‌شود؛ تکمیل جدیدتر سبد، رهاشدگی قبلی را بی‌اثر می‌کند. چون شناسه‌ی سبد موجود نیست، فعلاً برای هر مشتری یک جریان سبد فرض می‌شود.

سناریوهای `C013` تا `C017` به‌ترتیب نبود رضایت، شکایت با خستگی پیام، ارسال رایگان با کانال جایگزین، یادآوری سبد و خرید تکمیل‌شده را پوشش می‌دهند. `C003` محدودیت پیام و `C010` عدم مزاحمت را بررسی می‌کنند.

داشبورد تعاملی نمونه در `landing/index.html` خلاصه‌ی پیشنهادها، فیلتر فوریت/رسیدگی/کانال و جزئیات دلیل هر مشتری را نمایش می‌دهد. اگر صفحه از همان دامنه‌ی API (مسیر `/dashboard`) باز شود، پیشنهادها از `/next-best-action` خوانده می‌شوند؛ در غیر این صورت، مثل GitHub Pages، نسخه‌ی نمونه‌ی محلی نمایش داده می‌شود. منبع فعال داده در بالای داشبورد نوشته می‌شود.

برای سرو کردن صفحه و API از یک منبع، مثل محیط توسعه‌ی محلی، متغیر `VAFA_CORS_ORIGINS` لازم نیست؛ فقط API را اجرا کنید و `/dashboard` را باز کنید. اگر رابط را روی دامنه‌ی دیگری میزبانی می‌کنید، همان دامنه را در `VAFA_CORS_ORIGINS` (با کاما جدا کنید) بدهید. این پروژه هیچ احراز هویتی ندارد؛ بنابراین فقط از داده‌ی ساختگی استفاده کنید.

## مدیریت کمپین (حافظه‌ی موقت)

این بخش فقط صف بررسی است؛ هیچ پیامی ارسال نمی‌شود و داده‌ها با ری‌استارت سرویس پاک می‌شوند.

| مسیر | کاری که انجام می‌دهد |
|---|---|
| `POST /campaigns/preview?customer_id=C001&as_of=2026-07-24` | پیش‌نمایش پیام و کانال؛ برای مشتری بدون رضایت یا با عدم مزاحمت: ۴۲۲ |
| `POST /campaigns?customer_ids=C001&customer_ids=C002&as_of=2026-07-24` | ساخت کمپین pending؛ مشتری ناموجود ۴۰۴، عدم رضایت ۴۲۲، کمپین تکراری ۴۰۹ |
| `PATCH /campaigns/{id}` با `{"message_fa": "..."}` | ویرایش متن فقط در وضعیت pending |
| `POST /campaigns/{id}/approve` یا `/cancel` | تغییر وضعیت؛ بررسی دوباره ۴۰۹ |
| `POST /campaigns/{id}/reject` با `{"reason": "..."}` | رد با دلیل اجباری |
| `GET /campaigns?status=pending` و `GET /campaigns/summary` | فهرست و خلاصه‌ی وضعیت‌ها |

متن اصلی پیشنهاد در `original_message_fa` نگه داشته می‌شود تا تصمیم‌های ویرایش‌شده قابل ردیابی باشند.

## باشگاه مشتریان، مسیر خودکار و اتصال‌ها

سه ماژول دیگر روی همان داده‌ی ساختگی کار می‌کنند؛ وضعیتشان در حافظه است و با ری‌استارت پاک می‌شود. اعداد اعتبار و کوپن فقط محاسباتی است و روی سفارش واقعی اعمال نمی‌شود.

| مسیر | کاری که انجام می‌دهد |
|---|---|
| `GET /loyalty/segments?as_of=2026-07-24` | بخش‌بندی RFM هر مشتری (وفادار ارزشمند، وفادار، تازه‌وارد، در خطر ریزش، غیرفعال) و شمارش هر بخش |
| `GET /loyalty/customers/C006` | پروفایل مشتری با امتیاز RFM، بخش و نسبت ریسک ریزش |
| `GET /loyalty/points?customer_id=C001` | موجودی امتیاز از خریدها و پاداش باشگاه |
| `POST /loyalty/points?customer_id=C001` با `{"points": 100, "reason": "..."}` | ثبت امتیاز دستی؛ امتیاز منفی بیشتر از موجودی ۴۲۲ |
| `POST /loyalty/customers/C001/credit` با `{"points": 50}` | تبدیل امتیاز به اعتبار کیف پول (هر امتیاز ۱۰۰۰ تومان، انقضا ۹۰ روز) |
| `POST /loyalty/coupons` با `{"customer_id": "C002", "discount_toman": 100000}` | صدور کوپن اختصاصی؛ سقف تخفیف ۵۰۰٬۰۰۰ تومان |
| `POST /loyalty/coupons/{code}/validate` با `{"order_value_toman": 700000}` | اعتبارسنجی کد، محاسبه‌ی مبلغ نهایی؛ منقضی/باطل‌شده ۴۲۲ |
| `POST /automation` | ساخت مسیر خودکار با تریگر `cart_abandoned`، `complaint` یا `churn_risk` و حداکثر ۶ مرحله |
| `POST /automation/{id}/schedule` با `{"customer_id": "C001"}` | برنامه‌ی زمانی هر مرحله؛ ساعت مجاز ۹ تا ۲۱ و سقف ۲ پیام در هفته |
| `POST /automation/{id}/pause` و `/resume` | توقف و فعال‌سازی مسیر |
| `POST /integrations/tokens` با `{"name": "...", "scopes": ["recommendations:read"]}` | توکن دسترسی محدود؛ مسیر `/integrations/protected/recommendations` بدون توکن ۴۰۱ و بدون دسترسی ۴۰۳ |
| `POST /integrations/webhooks` با `{"url": "https://...", "events": ["campaign.approved"]}` | ثبت وبهوک و دریافت secret امضا |
| `POST /integrations/webhooks/{id}/deliveries` | محاسبه‌ی امضای HMAC-SHA256 و برنامه‌ی تلاش مجدد (`?simulate_failure=true`) |
| `GET|POST /integrations/branches` | فهرست شهرها با تعداد مشتری و علامت‌گذاری شعبه |

پیش‌نویس مسئله‌های آینده با اولویت و معیار پذیرش در [`docs/future-issues.json`](docs/future-issues.json) است؛ این‌ها **در GitHub ثبت نشده‌اند**. وضعیت Issueهای آنلاین نیز در این اجرا قابل بررسی نبود. پیش از اتصال داده‌ی واقعی، احراز هویت و جداسازی فروشگاه‌ها ضروری است.

## دیدن لندینگ‌پیج

فایل `landing/index.html` یک صفحه‌ی استاتیک است؛ کافیست آن را در مرورگر خودتان باز کنید (نیازی به سرور نیست).

## چرا rule-based در فاز اول؟

خرده‌فروش به یک جعبه‌سیاه اعتماد نمی‌کند که margin و ارتباط با مشتری‌اش را دستش بدهد. هر خروجی موتور یک `reason_fa` دارد که دلیل تصمیم را شفاف توضیح می‌دهد. جزئیات کامل در [`docs/architecture.md`](docs/architecture.md).
